# Public Repo Operating Rhythm

## Purpose
This note defines how GitHub should function as the project's ongoing public home rather than a static publication mirror.

The aim is to make public progress legible, invite meaningful contribution, and keep the visible repository aligned with the real execution path of the project.

## Core Principle
Every meaningful internal planning increment should be checked for a public-facing counterpart.

Possible public-facing counterparts include:
- a bounded artifact document;
- a contributor-facing rationale note;
- a research prompt;
- a pilot entry draft;
- a reviewer packet;
- an issue prompt;
- a concise update note.

The public layer should lag internal reasoning slightly, but it should not drift so far behind that the repository becomes stale or decorative.

## What the Public Repo Should Regularly Show
The repository should repeatedly make five things visible:
1. what the current artifact is;
2. what changed recently;
3. what help is useful right now;
4. what remains intentionally non-public;
5. what the next concrete contribution surfaces are.

## Ongoing Rhythm

### 1. Artifact progress rhythm
When the internal workspace produces a durable artifact increment, ask:
- can this be published directly?
- if not, can it be converted into a contributor-facing version?
- if not, what smaller public-facing derivative should exist instead?

Examples:
- internal decision -> public decisions summary
- broad research queue -> contributor research prompts
- entry drafting progress -> pilot entry issue prompt
- review method -> public review packet or checklist

### 2. Contribution rhythm
The public repo should always expose at least one concrete contribution path.
Prefer contribution surfaces like:
- source-finding tasks for a specific concept;
- issue prompts for a pilot entry;
- wording review requests;
- format and workflow review requests;
- public/private boundary feedback.

Avoid leaving the repository in a state where interested contributors can only admire the project but not act on it.

### 3. Update rhythm
The repo does not need constant broadcasting, but it should not go silent for long stretches.
A lightweight rhythm is enough if each update is concrete.

Recommended visible update types:
- a new or revised artifact file;
- a new pilot-entry draft;
- a new issue prompt or contributor packet;
- a short update note summarizing what advanced and what help is needed.

### 4. Boundary rhythm
Public openness does not mean total exposure.
At regular intervals, check whether:
- internal state-management files remain private;
- public docs are still legible without internal scaffolding;
- hidden architecture is not crowding out practical value;
- contributor-facing materials are staying specific and useful.

### 5. Feedback rhythm
When public-facing materials exist, the project should periodically harvest and compress feedback:
- what contributors found unclear;
- what requests were too broad or too vague;
- what sources or issue prompts actually produced useful input;
- what public materials created interest without producing actionable help.

That feedback should flow back into artifact scope, issue design, and contribution docs.

## Minimum Public-Home Standard
GitHub is functioning as the project's real public home when a newcomer can quickly see:
- the current artifact track;
- why it matters;
- what is ready for collaboration;
- what exact work they can pick up next;
- and evidence that the project is actually moving.

## Session-Level Integration Rule
For each meaningful work session, ask before finishing:
1. what changed internally?
2. what part of that should become public now?
3. what part should remain internal for now?
4. what new contributor-facing entry point should be added or updated?

If a session makes meaningful progress but creates no plausible public-facing derivative, that is a warning sign that the work may be too internal, too abstract, or too disconnected from the collaboration surface.

## Near-Term Public Rhythm for dot-r
For the current lexicon phase, the public rhythm should prioritize:
1. repository orientation docs;
2. public decisions and research prompt notes;
3. the minimum-research-inputs note for the first three pilot concepts;
4. the concept note for the lexicon MVP;
5. the first three pilot entries;
6. issue prompts or contribution packets tied to those entries;
7. a compact reviewer packet.

## Working Conclusion
The public repo should behave like a living workshop around a serious heavy-AI public-interest use case.
It should feel active, bounded, inspectable, and useful.
It should not feel like a branding shell around private thinking.
